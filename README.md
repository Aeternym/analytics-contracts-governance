# Analytics Contracts Governance

### Аудит и управление аналитическими контрактами

**Бизнес-анализ · Data Governance · Метрики и KPI · Python · Контроль качества данных**

[![Автоматические проверки](https://github.com/Aeternym/analytics-contracts-governance/actions/workflows/ci.yml/badge.svg)](https://github.com/Aeternym/analytics-contracts-governance/actions/workflows/ci.yml)

Этот проект показывает, как превратить разрозненные описания бизнес-метрик в управляемый каталог аналитических контрактов: с едиными правилами документирования, ответственными за определения, связями между объектами и проверками качества.

В основе проекта — аудит каталога аналитических контрактов, выполненный мной **в рамках обучения аналитической специализации во время работы в HOLODILNIK.RU**. Позже для портфолио я подготовил отдельный технический прототип: Python-валидатор и полностью вымышленные примеры контрактов.

> **Важно:** исторический аудит и нынешний Python-прототип — разные этапы работы. Автоматический валидатор **не внедрялся в компании** и не был результатом исходного аудита. Исходные внутренние документы и бизнес-определения работодателя в публичный проект не включены.

## Задача

Метрика не становится понятной только потому, что у неё есть название и формула. Для воспроизводимой аналитики необходимо договориться:

- **Что именно измеряем:** бизнес-смысл, единица подсчёта и правила расчёта.
- **Какие данные включаем и исключаем:** статусы, события, тестовые записи и спорные случаи.
- **За какой период считаем:** временные границы и правила сравнения.
- **Как анализируем результат:** допустимые измерения, сегменты и аналитические разрезы.
- **Кто принимает решения:** владелец определения, согласующие и потребители метрики.
- **Когда определение готово к использованию:** статус, критерии приёмки и процедура пересмотра.

Целевая логика каталога:

**Бизнес-вопрос → дашборд → метрика → измерения, сегменты и сравнения.**

Каждый объект должен иметь стабильный идентификатор и понятные связи с другими объектами. Изменения должны быть проверяемыми и проходить согласование.

## Часть 1. Аудит аналитических контрактов

### Масштаб исходного анализа

| Объект | Количество |
| --- | ---: |
| Файлы исходного каталога, включённые в аудит | **42** |
| Контракты метрик | **15** |
| Бизнес-измерения | **5** |
| Сегменты | **3** |
| Бизнес-домены | **7** |
| Стандарты оформления | **2** |
| Шаблоны документов | **7** |

Исходный каталог рассматривался как **система связанных бизнес-определений**, а не просто набор Markdown-файлов.

### Что я анализировал

1. Структуру файлов, шаблоны и единообразие обязательных полей.
2. Определения метрик, правила включения и исключения, периоды и спорные сценарии.
3. Наличие владельцев, согласующих, бизнес-доменов и потребителей аналитики.
4. Соответствие заявленных разрезов реальным ссылкам на измерения и сегменты.
5. Уникальность идентификаторов и корректность связей между контрактами.
6. Статусы жизненного цикла и критерии готовности к согласованию.

### Основные выводы аудита

| Обнаруженная проблема | Почему это важно |
| --- | --- |
| Не заполнены владельцы и согласующие | Некому принять решение по спорному определению и подтвердить его актуальность. |
| Домены существуют, но связи с контрактами не заполнены | Сложно понять, какие метрики относятся к конкретному бизнес-направлению. |
| Нет формализованных контрактов дашбордов и потребителей | Не прослеживается путь от бизнес-решения до конкретной метрики. |
| Метаданные местами расходятся с текстом карточек | Одна и та же метрика может интерпретироваться по-разному. |
| Машиночитаемые критерии приёмки не заполнены | Готовность определения нельзя надёжно проверить автоматически. |
| Шаблоны и реальные карточки не полностью согласованы | Новые документы могут наследовать структурные ошибки. |

На момент аудита карточки метрик, измерений и сегментов оставались в статусе **`draft`**. Поэтому результат аудита — не «готовый к внедрению единый источник истины», а **диагностика состояния каталога и план его развития**.

### Подготовленные аналитические результаты

- Приоритизированный **backlog** проблем и доработок.
- Поэтапный **roadmap** развития каталога.
- Рекомендации по закреплению владельцев метрик и процедуре согласования.
- Чек-листы полноты контрактов и критерии готовности к `review`.
- Вопросы для интервью с владельцами бизнес-определений.
- Требования к будущей автоматической проверке структуры и связей.

Методика и предлагаемые следующие шаги представлены в документах: [метод аудита](docs/audit_method.md), [готовность к review](docs/review_readiness.md) и [приоритизация](docs/prioritization.md).

## Часть 2. Демонстрационный Python-валидатор

После аудита я создал отдельный **портфельный прототип** для проверки идеи автоматизированного контроля аналитических контрактов.

Прототип принимает каталог Markdown-файлов с метаданными в начале документа, проверяет некоторые структурные правила и формирует JSON-отчёт. Его можно запускать вручную или в CI.

```mermaid
flowchart LR
    A["Markdown-контракты"] --> B["Разбор метаданных"]
    B --> C["Проверки структуры и ID"]
    C --> D["Проверка ссылок"]
    D --> E["JSON-отчёт и код выхода"]
```

### Что проверяет прототип

| Проверка | Поведение |
| --- | --- |
| Источник данных | Отсутствующий путь или пустой каталог считаются ошибкой по умолчанию. |
| Формат карточки | Проверяется наличие и возможность разбора простого блока метаданных (*front matter*). |
| Идентификатор | Проверяется формат ID для типа контракта и отсутствие дублей. |
| Статус | Проверяется допустимое значение для каждого типа объекта. |
| Ответственный | Для статусов `review` и `approved` требуется заполненный `owner_id`. |
| Критерии приёмки | Для метрик в статусах `review` и `approved` проверяется наличие непустого поля `acceptance_criteria`. |
| Ссылки | Проверяется существование связанных ID и соответствие ожидаемому типу объекта. |
| Результат | Формируется `PASS` либо `NOT_READY`; при ошибках CLI возвращает ненулевой код завершения. |

Это **структурный контроль**, а не автоматическая экспертиза бизнес-смысла. Программа не подтверждает корректность формул, полноту методологии, достоверность показателей или согласование метрики реальными владельцами.

### Синтетические данные

В папке [`examples/contracts`](examples/contracts) находится **6 полностью вымышленных контрактов**:

| Тип | Количество | Пример |
| --- | ---: | --- |
| Метрика | 2 | Завершённые заказы; повторные заказы |
| Измерение | 1 | Канал `web` / `app` |
| Сегмент | 1 | Новый клиент |
| Домен | 1 | Демонстрационная коммерция |
| Владелец | 1 | Вымышленная роль |

Пример с завершёнными заказами находится в статусе `review` и содержит ссылки на измерение, сегмент и роль владельца. Пример с повторными заказами намеренно остаётся в `draft`: для него не определено окно истории.

Примеры показывают правила проверки и **не воспроизводят реальные корпоративные метрики**.

## Быстрый запуск

Требуется **Python 3.11+**. У проекта нет дополнительных зависимостей для выполнения валидатора; для установки используется стандартный механизм `pip`.

```bash
# Создать виртуальное окружение
python -m venv .venv

# Активировать окружение:
# Windows PowerShell: .venv\Scripts\Activate.ps1
# macOS / Linux:     source .venv/bin/activate

# Установить проект локально
python -m pip install -e .

# Проверить синтетический каталог и сохранить отчёт
python -m contracts_governance.cli examples/contracts --output reports/demo_validation.json

# Запустить тесты
python -m unittest discover -s tests -v
```

После проверки корректного демонстрационного каталога ожидается результат:

```json
{
  "files_scanned": 6,
  "contracts_parsed": 6,
  "issues": [],
  "errors": 0,
  "verdict": "PASS"
}
```

Это сокращённый фрагмент отчёта: фактический JSON также содержит путь к каталогу, счётчики по типам объектов и сведения об источнике.

По умолчанию отсутствующий или пустой каталог приводит к `NOT_READY`. Флаг `--allow-empty` разрешает только **существующий пустой каталог**, если это явно предусмотренный сценарий; отсутствующую директорию он не скрывает.

## Тестирование и CI

В проекте есть **10 автоматических тестов** на `unittest`:

- успешная проверка синтетического каталога;
- отсутствующая директория и ненулевой код CLI;
- пустой каталог и явное разрешение `--allow-empty`;
- дубли идентификаторов;
- недопустимые статусы;
- несуществующие ссылки;
- ссылки на объект неправильного типа, включая владельца.

В репозитории настроен [GitHub Actions workflow](.github/workflows/ci.yml): на каждый push и pull request он запускает 10 тестов и проверяет синтетический каталог из 6 контрактов. Текущий статус виден на бейдже в начале README.

## Ограничения и дальнейшее развитие

Прототип демонстрирует подход, но не является промышленной системой Data Governance.

**Текущие ограничения:**

- Парсер поддерживает только простой YAML-подобный формат, **не полный YAML**.
- Проверяются наличие и типы некоторых связей, но не вся семантика контрактов.
- Нет проверки достоверности формул, SQL-расчётов и фактических значений метрик.
- Не реализованы полноценный контроль переходов между статусами и согласование изменений.
- Нет интеграции с промышленным DWH, BI-платформой или корпоративным каталогом.

Следующие логичные шаги: полноценный YAML-парсер и версионируемая схема, более строгие правила обязательных полей, проверки Markdown-ссылок и шаблонов, контроль жизненного цикла, проверки изменённых файлов в CI, генерация документации из утверждённой версии каталога.

Подробнее: [технический замысел](docs/automation_design.md) и [ограничения парсера](docs/parser_limitations.md).
